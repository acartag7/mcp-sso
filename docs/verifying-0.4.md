# Verifying the 0.4.0 multi-resource change

Everything in this document is **maintainer-run**. The self-hosted workflows are
dispatch-only, and the final gate needs a live deployment, so neither can be
completed from a development machine.

## What has already been verified, and how

Locally, against the exact branch head:

- **1035 tests, zero skipped** — including the shared store-conformance suite run
  against a **live MySQL 8.4**, not only memory and SQLite. The MySQL suites skip
  silently when `MYSQL_URL` is unset, so a bare `pnpm test` reports ~995 and store
  parity goes untested: always set it before claiming a full run.
- **A two-resource end-to-end proof** driving the **official MCP SDK client** over
  a real loopback socket (`test/e2e-mcp-sdk-multi-resource.test.ts`): two live
  endpoints on one issuer, a full grant each, then every cross-resource negative
  at HTTP level — a token for A rejected at B with B's own challenge, A's refresh
  refused at B, replay revoking only A's family.
- **An upgrade test built from the released artifact**: the fixture is generated by
  executing v0.3.2's own migration code, not a hand-written guess at its schema.
- **The shipped two-resource example is driven by tests**
  (`test/example-multi-resource.test.ts`): per-resource PRM, per-endpoint
  challenge, fail-closed boot on blank config, a token minted for one resource
  refused at the other, and the Origin gate. The example is what the live gate
  below points an MCP client at, so it is executed here rather than only
  typechecked.
- **A cross-slice security suite** (`test/cross-slice-security.test.ts`) that
  re-asserts every slice's security property against whatever is in the tree.
  This exists because two earlier fixes were silently reverted when a later slice
  rewrote the same files, and per-branch tests could not see it.
- Every fix **mutation-verified**: reverting it in isolation reddens exactly its
  regression test.
- typecheck · `check:lines` · `check:seams` · build · `npm pack --dry-run` ·
  process guard.

On the self-hosted runners, by maintainer dispatch (the workflows do not trigger
on `pull_request` — see the boundary rule in `AGENTS.md`):

- **CI** — typecheck · `check:lines` · test · build · `process-guard`, plus
  `attest-dispatched-checks`, which publishes the two branch-protection contexts
  only after both enforcing jobs pass.
- **CodeQL** — `javascript-typescript` analysis.

Re-dispatch both after every push: a green run on a superseded head proves
nothing about what merges. Confirm the run's head SHA equals the PR head.

## What has NOT been verified

1. **Machine-client CAS methods are exercised only through test doubles.** No
   shipped store implements `MachineClientStore` — machine clients are
   provisioned out of band by design — so resource binding for that path has
   never run against SQLite or MySQL.
2. **No real-client interop.** The official SDK used as a library is not the
   deployed client in Claude Code, claude.ai or ChatGPT. This is the largest
   untested assumption in the release and the gate for tagging 0.4.0.

evidence: a dispatch against a stale ref proves nothing about what merges.

## 2. Real-client gate — required before tagging 0.4.0

Static review cannot answer whether real clients follow **path-inserted PRM URLs**
for two sibling resources on one host. That is the single largest untested
assumption in this change.

Stand up two resources on one issuer, e.g. `/grafana/mcp` and `/memory/mcp`, then
for each of Claude Code, claude.ai and ChatGPT:

1. discovery reaches the correct per-resource PRM document;
2. authorize → consent → token completes for resource A;
3. the tool call succeeds at A;
4. **A's token is rejected at B** — the property the feature exists for;
5. refresh works at A and is refused when it names B.

Record client and version for each result. If a client cannot follow same-origin
path-specific PRM, the recorded fallback is one resource per subdomain with a
single-resource adapter mount.

## 3. Upgrade rehearsal — required before tagging 0.4.0

0.4.0 is a **breaking** upgrade: pre-0.4 refresh tokens and machine credentials
stop working and every user re-authorizes once. See
[`upgrading-0.4.md`](upgrading-0.4.md).

Rehearse it against a database written by the **registry** 0.3.2 package, not a
local build:

1. install `mcp-sso@0.3.2` from npm and run a full grant against SQLite, then MySQL;
2. drain the 0.3.2 handler — the cutover is stop-the-world with respect to
   pre-0.4 token handlers, which ignore the new resource columns;
3. start 0.4.0 against the same store and confirm: a new authorization completes,
   a pre-0.4 refresh token is refused with `invalid_grant`, and re-authorization
   re-offers previously approved scopes rather than starting from nothing;
4. confirm rollback is only attempted from an isolated pre-cutover snapshot.

## Deliberate decisions recorded for the audit trail

- **A frozen acceptance test was edited** (`test/acceptance/cimd/s6b-scope.test.ts`)
  and its manifest hash regenerated, with explicit owner approval. The suite
  seeds pre-0.4 rows to test prior-grant *accumulation*; once legacy binding
  required the explicit attestation, its CONTROL row could no longer accumulate.
  The fixture now attests its own seeded rows. The enforcement was not weakened —
  only the fixture's declared intent changed.
- **All PENDING/NOT-ENFORCED markers were removed** from the contract set. That is
  the activation slice's job, and every removed marker traces to shipped code.
